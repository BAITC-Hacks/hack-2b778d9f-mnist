# Проверка записей и извлечённых поручений

`cases.json` — матрица испытаний. `simulated.json` — собственные короткие сценарии с вымышленными именами и ожидаемым смыслом результата. Аудио в эти файлы не встроено. Все реальные модельные прогоны первоначально имеют статус `pending`.

Пути в JSON заданы относительно корня репозитория. Для случаев трека `audio_path` и `reference_path` указывают на локальные файлы `track/`; полные транскрипты и аудио здесь не копируются. `evaluation_meeting_date` — заданная опора испытания, не утверждение о дате исходного совещания. Там, где дата записи неизвестна, точную нормализацию относительных сроков не оценивают как установленный факт.

## Формат и материалы

| Файл/поле | Значение |
| --- | --- |
| `cases.json` → `cases` | Два штатных RU-примера и отдельные simulated RU, KK, mixed, overlap, silence |
| `expected_actions` | Семантические группы ожидаемых поручений, исполнитель и исходный срок; формулировка может отличаться |
| `deadline_policy` | `preserve_phrase_review`, `exact_date` или `absent`: как оценивать срок |
| `fixture_id` | ID соответствующего случая в `simulated.json` |
| `simulated.json` → `fixtures` | Дата, список участников, план реплик и ожидаемые действия/кандидаты |
| `turns[].start/end` | План времени записи; при создании аудио заменить фактической разметкой в отдельном отчёте |
| `expected_speaker_id` | Роль в сценарии, не обязательное имя кластера pyannote; кластеры можно перенумеровывать |

Без GPU можно проверить целостность JSON:

```bash
python3 -m json.tool evaluation/cases.json > /dev/null
python3 -m json.tool evaluation/simulated.json > /dev/null
```

Это проверяет формат данных, не модели. Для конкретного модельного запуска использовать команду smoke-проверки из README приложения и передавать выбранный `audio_path` и `evaluation_meeting_date`. Сохранить возвращённый ID совещания, его JSON и собственный отчёт. При отсутствии аудио у simulated-случая отметить `pending`; текстовый запуск извлечения можно выполнить отдельно и назвать проверкой извлечения из эталонного текста.

## Прогон с изоляцией сети на уровне Linux

`backend/scripts/offline_smoke.sh` создаёт новые user/network namespaces через `unshare --user --map-root-user --net`. В новом сетевом пространстве включается только loopback, запускается собственный `ollama serve`, затем тот же `brev_smoke.py`. Модельные процессы и конвертер наследуют это пространство. Скрипт проверяет изменение идентификатора namespace и не продолжает выполнение, если `unshare` запрещён. Это отдельная проверка от Python audit hook: ограничение одного Python-процесса не изолирует внешний Ollama.

Перед запуском должны быть установлены `unshare`, `ip`, `curl`, Ollama и готовое Python-окружение; все веса предварительно загружены на машину. Каталоги ASR, pyannote и Ollama обязательны и должны быть доступны пользователю. Скрипт не скачивает модели. Для другого сервера заменить пути окружения:

```bash
export MEETING_PYTHON=/data/venvs/project/bin/python
export ASR_MODEL_PATH=/data/models/kazakh-whisper-large-v3-turbo
export PYANNOTE_DIARIZATION_MODEL=/data/models/speaker-diarization-community-1
export OLLAMA_MODELS=/usr/share/ollama/.ollama/models

bash backend/scripts/offline_smoke.sh 'track/Совещание №1.mp3' \
  --meeting-date 2026-09-23 \
  --data-dir /data/offline-meeting-1 \
  --report /data/offline-meeting-1/report.json \
  --result /data/offline-meeting-1/result.json

bash backend/scripts/offline_smoke.sh 'track/Совещание №2.mp3' \
  --meeting-date 2026-09-23 \
  --data-dir /data/offline-meeting-2 \
  --report /data/offline-meeting-2/report.json \
  --result /data/offline-meeting-2/result.json
```

Запускать команды из корня репозитория. `--result` содержит полный локальный результат: не переносить его в публичные артефакты без проверки. Дата в командах остаётся тестовой опорой. Для данного рабочего сеанса пользователь разрешил обработку обеих предоставленных записей на Brev.

Изоляция обеспечивает отдельный localhost; уже работающий Ollama хоста не используется и не завершается. Обработчик `trap` останавливает только дочерний Ollama этого запуска. Переменные `MEETING_NETWORK_ISOLATION=linux_network_namespace` и `MEETING_NETWORK_NAMESPACE` передаются в runner для отчёта; сообщение stderr содержит идентификаторы пространств. Успешный запуск `unshare` проверяет доступность механизма. Доказательством работы конвейера без внешней сети является завершённый smoke внутри этого пространства с сохранённым отчётом, а не один запуск проверки namespace. Ошибку изоляции нельзя превращать в обычный сетевой прогон с отметкой offline.

## Как подготовить собственное аудио

1. Озвучить реплики `simulated.json` разрешёнными участниками либо локальным синтезатором. Не использовать внешнее speech API. В диалоге должны различаться реальные голоса; несколько имён при одном голосе не являются проверкой диаризации.
2. Для RU/KK/mixed сохранить отдельные записи. Для overlap действительно наложить два разных голоса в указанном месте; одна последовательность реплик не проверяет наложение.
3. Сохранить запись локально, записать её хеш, фактические интервалы и способ создания. Не приписывать будущему файлу качество по одному сценарному тексту.
4. Для тишины использовать короткий PCM WAV без речи. Ожидается явный пустой результат или понятное сообщение о невозможности распознавания, без выдуманных поручений.

## Как оценивать

Сначала проверить сырой автоматический результат, затем время и объём ручного исправления. Не включать исправленные поля в метрику автоматического извлечения.

Сопоставлять поручения по смыслу, исполнителю и сроку. Одну группу эталона можно разбить на несколько действий; одно действие может корректно объединять группу. В отчёте явно указать соответствия, чтобы дробление не увеличивало искусственно число найденных поручений. Лишнее неподтверждённое предложение в разделе кандидатов допустимо; превращение его в подтверждённое поручение — ошибка.

Для каждого случая записывать:

- настройки моделей, версии, GPU, длительность записи, время этапов и пик VRAM;
- число найденных ожидаемых групп, пропуски и ложные поручения;
- правильного/неправильного/неустановленного исполнителя и срока отдельно;
- сохранность ключевых чисел, имён и RU/KK переходов;
- сопоставление говорящих с ручной разметкой, реальные наложения и явную неопределённость;
- ошибки саммари и совпадение сохранённых правок с экспортом.

При достаточной разметке можно посчитать precision = верные извлечённые поручения / все извлечённые поручения и recall = найденные ожидаемые группы / все ожидаемые группы. Перед подсчётом определить, что считать одной группой, и отделить спорные эталоны. WER/CER и ошибки диаризации считать отдельно; не получать их из числа поручений. Небольшая матрица демонстрирует конкретные случаи, а не гарантирует качество на любых совещаниях.

## Неоднозначности предоставленных эталонов

- В обоих документах не задана надёжная дата совещания. Год сроков вида «15 октября» отсутствует. `2026-09-23` используется только как тестовый вход; нельзя выдавать его за дату записи.
- В №1 срок аудита обсуждается как две, затем три недели, затем 15 октября. Ожидается последнее подтверждённое содержание, сохранение исходного срока и проверка при противоречии.
- В №1 «к среде» может означать текущий либо следующий такой день в зависимости от реального контекста; неделя — интервал, а не автоматически выбранная календарная дата.
- В №2 сначала претензия назначена Ерлану до конца недели, а итоговая реплика обобщает её вместе с работой Ботагоз и двумя неделями. Табличный эталон выбирает первое назначение. Нужна пометка неоднозначности/проверка, а не молчаливая подмена.
- В №2 обучение должно закрыть очередь за месяц, а смета — за неделю. Это разные результаты с разными сроками; недельный срок нельзя присваивать завершению всей переаттестации.
- В №2 «после совещания с подрядчиками» — событие, не календарная дата. Пять рабочих дней — условие будущего договора, не срок подготовки уведомления/шаблона. У последнего поручения срок не указан.

Эти случаи отражены в `ambiguities` и `deadline_policy` матрицы. Любое исправление эталона должно ссылаться на локальное аудио и иметь объяснение проверяющего.
