# План доведения MVP до требований HackAlem

Дата: 23 сентября 2026 года. Источники: [задание трека](../track/HackAlem%20AI_%20Система%20автопротоколирования%20совещаний%20с%20фиксацией%20поручений.md), [функциональная спецификация](../spec-meeting-minutes-assistant.md), [модель предметной области](../CONTEXT.md). Исследование выбранных моделей: [первичные источники и ограничения](research/2026-09-23-model-selection.md).

Статус: исправления выполняются. Этот документ задаёт проверяемый план и не является свидетельством успешных модельных испытаний. Состояние реальных прогонов должно сопровождаться отчётом с записью, версиями моделей, измерениями и замечаниями проверяющего.

## Что оценивает трек

| Обязательство | Проверяемый результат |
| --- | --- |
| Русский, казахский и смешанная речь | Отдельная разрешённая запись каждого типа проходит полный конвейер; сохранены имена, числа и смысл поручений |
| Диаризация и привязка к человеку | Реплики различаются по speaker ID; человек может подтвердить имена; ответственный не подменяется говорящим |
| Автоматические поручения | Извлечены действие, явно назначенный исполнитель, срок как сказано и основание; отсутствующие поля видны |
| Саммари и транскрипт | Содержание доступно для проверки и правки, спорные фрагменты можно прослушать |
| Экспорт | Скачивается пригодный DOCX или PDF с сохранёнными правками; неподтверждённый результат помечен черновиком |
| Локальное выполнение и приватность | Аудио и производный текст не уходят во внешние AI API; разрешённые материалы хранятся локально и удаляются вместе с записью |
| Воспроизводимость | Репозиторий содержит приложение, зависимости, пути моделей, запуск и сценарий проверки |

Работоспособность, техническая реализация и README/воспроизводимость дают по 25 баллов, применимость — 15, развитие и оригинальность — 10. Поэтому готовый основной сценарий и проверяемая инструкция имеют преимущество перед расширением интерфейса.

Live-захват, подключение к конференциям, дашборд исполнения, напоминания, СЭД, рассылка и биометрическая идентификация отложены до выполнения обязательного сценария. Вход записью предусмотрен треком. Возможность локального размещения остаётся требованием; полноценное промышленное развёртывание не входит в минимум. Brev используется для разрешённого демо и сам по себе не подтверждает закрытый контур заказчика.

## Аудит исходного решения

Архитектура React/Vite + FastAPI + SQLite + файлы + один последовательный обработчик подходит для одной демо-машины. Сохраняем локальные ASR/диаризацию/LLM, ссылки на реплики, человеческие правки и маркировку черновика. Неопределённость исполнителя, времени или голоса должна оставаться видимой.

| Обнаруженный разрыв | Последствие | Исправление в текущей работе |
| --- | --- | --- |
| Код находился в `/tmp`, корневой README не описывал приложение | Проверяющий не может воспроизвести решение из репозитория | Перенос приложения и точный README |
| Только WAV при штатных MP3 трека | Невозможно загрузить предоставленные записи | Локальное декодирование MP3, проверка размера, длительности и реального формата |
| Имя из списка участников считалось достаточным подтверждением ответственного | Возможное выдуманное назначение | Проверять свидетельство в репликах, иначе сохранять неопределённость |
| Срок нормализовался без подтверждения исходной фразой | Ложная дата в протоколе | Сохранять фразу, проверять источник, нормализовать только однозначные выражения |
| Неполная валидация вложенных PATCH-полей | Повреждённые правки, ссылки или экспорт | Проверять типы, даты, временные интервалы, ссылки и человеческое подтверждение |
| При отказе PDF интерфейс терял доступ к готовому DOCX | Основной сценарий блокировался дополнительным форматом | Показывать доступный документ и отдельную ошибку конвертации |
| Один интервал диаризации должен был полностью покрывать ASR-сегмент | Паузы и погрешности границ скрывали даже единственного говорящего | Сопоставлять покрытие; настоящие смены голоса и наложения показывать отдельно |
| Пути ASR в инструкции не совпадали с загрузкой; окружение моделей не закреплено | Запуск из инструкции мог не работать | Согласованные каталоги, предварительная проверка артефактов и запись версий |
| Тесты использовали заменители моделей | Зелёные тесты не доказывали RU/KK/mixed качество | Отдельные реальные прогоны по матрице evaluation |

Это перечень исходных проблем. Завершённость исправления устанавливается проверкой ниже, а не наличием строки в таблице.

## Приоритеты и критерии приёмки

### P0 — воспроизводимый основной сценарий

1. Включить приложение в рабочий репозиторий, согласовать зависимости, переменные окружения, пути моделей и запуск через один backend worker.
2. Поддержать WAV и штатные MP3. Обе записи трека короче лимита 10 минут; они должны загружаться через тот же интерфейс, что использует проверяющий. Невалидный файл отклоняется до моделей.
3. Исправить основания ответственного и срока, валидацию правок и сохранение DOCX при отказе PDF. Фраза без календарного года не получает выдуманный год; список участников не устанавливает голос или назначение.
4. Обеспечить проверку человеком: прослушивание основания, исправление, сохранение, повторное открытие, скачивание. Предложение без проверенного подтверждения остаётся кандидатом.

Приёмка P0: backend проверки проходят; frontend собирается и проходит поведенческую проверку; MP3 принимается; правки переживают перезапуск; оба формата отражают сохранённые данные либо DOCX доступен с явной ошибкой PDF; удаление убирает запись и её файлы. Команды и результат приводятся в README/отчёте реализации. Модельные результаты этой приёмкой не подменяются.

### P1 — реальная модельная проверка

1. Проверить локальную загрузку ASR, Community-1 и Ollama; зафиксировать версии, ревизии весов, GPU, параметры контекста и генерации.
2. Обработать обе записи трека и проверить действия против [матрицы](../evaluation/cases.json). Разногласия эталонов разрешать прослушиванием, не подгонкой к табличной строке.
3. Записать с согласия участников или локально синтезировать материал по [собственным сценариям](../evaluation/simulated.json). Использовать разные голоса для проверки диаризации; одно TTS-чтение диалога не подтверждает несколько говорящих.
4. Отдельно проверить русский, казахский, переключение языков, неподтверждённое предложение, неизвестного исполнителя, сроки, тишину и наложение речи.
5. Повторить полный сценарий после предзагрузки моделей с запрещённым исходящим доступом, включая процесс локального Ollama. Сохранить результат проверки экспорта с казахскими символами.

Приёмка P1: каждый случай имеет аудио, настройки, результат и ручную оценку; отдельно записаны пропуски/ложные поручения, ошибки исполнителей/сроков, спорные голоса, время и VRAM. Отсутствующая запись или не выполненный прогон обозначены `pending`. Для объявления готовности не остаётся скрытых сбоев обязательного сценария; остаточные ошибки перечислены, неопределённые значения не представлены как факты. Проценты качества публикуются только с числителем, знаменателем и правилами оценки.

### P2 — удобство и развитие после приёмки

Улучшать скорость и расстановку говорящих по обнаруженным ошибкам. Затем выбирать одно расширение: надёжный захват микрофона с последующей полной обработкой либо дашборд проверенных поручений. Live-превью нуждается в отдельной проверке целостности фрагментов, задержек и очереди GPU; оно не заменяет P1. Рассылку и интеграции реализовывать по отдельному запросу.

## Что ещё требует доказательств

- Качество ASR и извлечения на обеих записях трека: ожидается реальный прогон.
- Казахский и смешанная речь с несколькими голосами: сценарии подготовлены, аудио и модельная оценка ожидаются.
- Наложение речи: сценарий подготовлен; времена в сценарии являются планом записи, не измеренной разметкой.
- Отсутствие внешней передачи, реальные DOCX/PDF, время и память: ожидаются испытания окружения.

Репозиторий не должен заявлять эти пункты проверенными до появления соответствующих результатов. Ни выбор модели по карточке, ни JSON нужной формы, ни тесты с заменителями не подтверждают семантическое качество.
